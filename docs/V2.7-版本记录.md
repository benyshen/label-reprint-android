# V2.7 版本记录（2026-11-26）

> 主题：**按 Zebra Link-OS 2.14 官方文档重做连接/打印/状态三件事**，修掉「显示已发送、纸不出来」。
> 依据：<https://techdocs.zebra.com/link-os/2-14/android/>（`BluetoothConnection`、`Connection`、
> `PrinterUtil` 三个类的官方说明与示例代码，jar 版本 v2.14.5198）。

## 1. 官方文档给出的三条事实（逐条对照我们的老代码）

| # | 官方原文（要点） | 我们的老代码 | 结论 |
|---|---|---|---|
| 1 | 蓝牙打印示例：`write(zplData.getBytes()); Thread.sleep(500); close();` 注释 "Make sure the data got to the printer before closing the connection" | `write()` 后 `sleep(400)` | 等待时间偏短（400 < 官方 500），且 sleep 之后**紧接着在同一条通道发状态命令** |
| 2 | 状态查询有**官方入口** `PrinterUtil.getCurrentStatus(Connection, PrinterLanguage)`，传 `PrinterLanguage.ZPL` 即走 `~HS` | 自己 `new PrinterStatusZpl(c)`，再退回 `currentStatus`（Link-OS JSON → ZR668 上 NPE） | 应该用官方入口 + 语言参数，而不是自己造 |
| 3 | SDK 为状态单独提供了 `BluetoothStatusConnection` / `TcpStatusConnection`（`*StatusConnection` 家族） | 状态查询与打印**共用同一条 SPP 通道** | **这就是「发完 ZPL 立刻查状态 → 作业不出纸」的根因**：等于往打印数据流里插命令 |

补充事实（官方 `PrinterUtil.getCurrentStatus` 文档）：`PrinterStatus` **只在创建时查询一次**，要最新值必须重新创建；
且"部分移动打印机（MZ 系列）在未就绪时根本不通信，本方法会抛 `ConnectionException`"。
ZR668 属于移动机，因此**状态查询失败是正常情况，不能当成打印失败**。

## 2. 改法（全部对齐官方）

| 项 | 现在怎么做 |
|---|---|
| 打印 | `open()` → `write(zpl.getBytes(UTF_8))` → `sleep(500)`（官方值）→ **打印路径里不再发任何状态命令** → 返回"已发送" |
| 状态通道 | 连接时按链路建 **`BluetoothStatusConnection`**（`Insecure` 配对则用 `BluetoothStatusConnectionInsecure`），与打印通道**完全分开**；BLE 机型（`BluetoothLeConnection`）SDK 没有对应 Status 类，退回主连接 |
| 状态查询 | 官方入口 `PrinterUtil.getCurrentStatus(conn, PrinterLanguage.ZPL)`（内部走 `~HS`，不碰 ZR668 上为 null 的 JSON 状态键） |
| 打印后静默 | 3s 内不查状态；BLE 场景下这段静默就靠它保护 |
| 连续失败退避 | 状态连续失败 3 次 → 暂停 60s，不再每 5s 去敲一条答不上来的链路 |
| 诊断 | 发送前把 ZPL 原文逐行打进日志（`PRINTZPL >>>`），现场"已发送但不出纸"时能直接判断是数据还是链路 |

## 5. 现场验收（三步，缺一步都别下结论）

1. **连上**：日志 `状态通道：BluetoothStatusConnection（独立于打印通道）`；
2. **打印**：日志顺序应为 `PRINT >>> ZPL N 字节` → `PRINTZPL >>> ^SD…/^XA…`（逐行）→ `PRINT >>> 成功 N ms`，
   **不再出现任何 `~HS`/状态命令夹在中间**；纸应当出来；
3. **若仍不出纸**：把 `PRINTZPL >>>` 那整段抓下来发我 —— 那段就是实际发给打印机的字节，
   可以直接复现（粘到 Labelary / 另一台机 / `adb` 直发），从而确定是内容问题还是这台机的链路问题。
