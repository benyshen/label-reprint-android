# V2.4 版本记录（2026-11-12）

> 主题：**文字 OCR 从 PP-OCRv4 升级到 PP-OCRv6 small**（det + rec + 18708 字统一字典）。
> 版式、ZPL、界面一行没动 —— 只换模型与字典，所以回归判据是「与 v4 基线逐字节/要素一致」。

## 1. 为什么升

工程里用的是 PP-OCRv4（2021 年的 mobile det/rec，6625 字字典）。PaddleOCR 后续已发到
**PP-OCRv6**（2026 年，tiny / small / medium 三档，官方宣称 det +4.9% / rec +5.1%，50 语言统一模型，
Apache-2.0）。现场痛点正好在 rec：仓库标签上那行 EAN-13 人眼可读串，v4 经常少认一位或多认一个引号
（`934024"512123` / `9340241512123`），v6 直接给全 13 位。

## 2. 换了什么（只三样）

| 项 | v4（旧） | v6（新） |
|---|---|---|
| det | `ch_PP-OCRv4_det_infer.onnx` 4.7MB | `ch_PP-OCRv6_det_small_infer.onnx` 9.9MB |
| rec | `ch_PP-OCRv4_rec_infer.onnx` 10.9MB | `ch_PP-OCRv6_rec_small_infer.onnx` 21.2MB |
| 字典 | `ppocr_keys_v1.txt` 6623 字 → 6625 类 | `ppocr_v6_dict.txt` 18708 字 → 18710 类 |
| cls | `ch_ppocr_mobile_v2.0_cls_infer.onnx` | 不变（180° 文本校正照旧） |

**推理流水线零改动**，因为 v6 与 v4 的契约一致（已逐个核过，不是猜的）：

- det：输入名 `x`，形状 `[N,3,H,W]` 全动态 → 现有「短边缩放到 736、pad 到 32 倍数」照用；
  输出单张 DB 概率图，`shape[-2]/shape[-1]` 取法不变；ImageNet mean/std 照用（`inference.yml` 的
  `NormalizeImage` 与 v4 同值，且图首节点直接吃 `x`，说明归一化没烘进模型）。
- rec：输入 `[N,3,48,W]`（高度固定 48，宽度动态）→ 现有「按全批最大长宽比定 imgW」照用；
  归一化 `(x/255-0.5)/0.5` 照用（图首同样是裸 Conv，没有内置归一化）。
- 字典导出顺序原样来自 `PP-OCRv6_small_rec_onnx/inference.yml` 的 `character_dict`（18708 条，
  无空行、无空格项、无重复），加上 CTC blank 与 use_space_char 正好 18710 = ONNX 的类别维度。

DB 后处理阈值**故意没动**（thresh 0.3 / box_thresh 0.5 / unclip 1.5）：v6 的 `inference.yml` 推荐
0.2 / 0.45 / 1.4，但同时改模型又改阈值，回归出问题就分不清是谁的锅。阈值留给下一轮单独 A/B。

## 3. 代码改动

- `ocr/OcrEngine.kt`：三个资产名常量 + 类注释（流水线本身没改）。
- `tools/ppocr_ref.py`：模型集可切换，`PPOCR_MODEL=v6|v4`（默认 v6），路径改为读本工程
  `android-app/.../assets/models`（v6）与 `android-app/models_v4`（v4 A/B 用，不进 APK）；
  类别数断言从写死 6625 改成按模型集断言。
- `tools/device_zpl_check.py`：**修掉一处假 FAIL 的根因** —— 它以前 `sys.path.insert` 到
  `E:/workspace/paddleocr-android-app/tools` 去 import 老 `ppocr_ref`（写死 v4），设备换 v6 后就会
  「PC 跑 v4、设备跑 v6」而报一堆假差异。现在用本工程同一份参考实现。
- 版本号 `versionCode 24` / `versionName 2.4`（界面从 PackageManager 读，未改 UI）。
- v4 三个模型文件从 `assets/models` 移到 `android-app/models_v4`：留在 assets 里等于白给 APK 加
  15.6MB，而它们只在 PC 端 A/B 时用。

## 4. 验证（都是真跑出来的数字）

### 4.1 PC 端 A/B：同一套预处理、同一批现场照片

`testImage/` 的 6 张现场照片，v4 与 v6 各跑一遍 det+rec：

| 照片 | v4 行数 / 平均置信 | v6 行数 / 平均置信 | 关键差异（条码 HRI 那行） |
|---|---|---|---|
| IMG_…224147 | 4 / 0.977 | 5 / 0.998 | `6"934024"512123` → `934024"512123` |
| IMG_…224153 | 7 / 0.739 | 5 / 0.998 | `934024512123` → **`6934024512123`** |
| IMG_…224159 | 5 / 0.823 | 4 / 1.000 | `934024512123` → **`6934024512123`** |
| IMG_…224209 | 5 / 0.984 | 5 / 1.000 | `9340241512123` → **`6934024512123`** |
| IMG_…224315 | 4 / 0.982 | 4 / 1.000 | `934024"512123` → `934024512123` |
| IMG_…224321 | 4 / 0.986 | 4 / 0.994 | `934024″512123` → `6"934024512123` |

det 耗时（同机 PC，736 短边）普遍 **-12% ~ -20%**（1717→1374ms、1711→1414ms、422→343ms）。

> 那行 HRI 文字在流水线里其实会被 `DROP`（判为条码的人眼可读串，归并进条码明文），所以它不是
> 复刻结果的直接来源 —— 但它是最能暴露 rec 质量的一行：v4 会在数字里插引号/丢首位，v6 不会。

### 4.2 真机（TC201L，Android 15，`com.tiaomabang.labelreprint` 2.4）

- 引擎启动：`models ready: … det=[x] rec=[x] cls=true dict=18710`（字典数对上 18710 类）。
- 内置样图 OCR：`--es all 1 --es ocr 1` → 3 张全部 2 行、置信 1.00，单张 546~593ms。
- 真实照片（`--es testImage … --es ocr 1`，1600×1393 校正图）：4 行文字全部 conf ≥ 0.98，
  「仓库标签 / 品名 / 五朵花纯净水」全对，OCR 757ms，`PLAN … elements=10 errors=0`。

### 4.3 双端逐字节 / 要素回归

```
python tools/device_zpl_check.py          → mismatches: 3   （V2.3 已知基线，未变）
python tools/device_zpl_check.py --ocr    → mismatches: 0   （3 张样图要素全一致，坐标差 ≤2 点）
python tools/regress.py                   → demo 5/5 通过
```

- 条码链那 3 个 mismatch 是 V2.3 就记录的已知差异（`^BY` 浮点取整、条高 87/83、模板基准选择），
  与本次换模型无关，**数字与 V2.3 完全一致**，说明几何/生成器没被碰到。
- OCR 链 `--ocr` 0 mismatch：PC 参考实现（v6）与设备端（v6）要素种类、文本完全一致。

## 6. 已知未做 / 下一轮

1. **没换 medium 档**（det 62MB / rec 76MB）：手机上 det 已经是 1.4s 级别，medium 只会更慢，收益不明。
   要更准就在 PC 端试 medium，端侧仍用 small。
2. **DB 阈值仍是 v4 口径**（0.3/0.5/1.5）——v6 官方建议 0.2/0.45/1.4，单独一轮 A/B 再定。
3. `tools/regress.py` 的 `[2] ZPL 校验` 里 3 个 `upload_*.zpl` / `t_5024_11.zpl` 报 `^FD != ^FS`：
   那是历史上传的原始 ZPL 样张（V2.0 就在库里），不是本工程生成器的产物，与本次改动无关。
