## 本版变更

### 1. 拍照页新增取景指示框（`ui/CaptureGuide.kt`）

- **框的长宽比 = 当前模板**（60/40、70/70、70/100）。框本身就在告诉用户"该拍成什么形状、该占多大"，
  不用猜该放多近。框外压 38% 黑遮罩，只留框内亮。
- 四角 L 形主色粗线当"对齐点"，中心十字给单条码/单行文字的标签一个对中点。
- 底部提示"标签四边对进框内 · 尽量占满"。
- **预览与拍照必须同画幅**（见下条），取景框画的矩形就是照片的实际范围。
- 框最大占画面 86%，横竖两个方向都会自动收敛，保证完整落在预览区内。
- **模板切换搬到了拍照页**（原先只在结果页）：形状不对时先在这改，不用拍完再去点。
  chip 文案（`模板3 70×100`）从模板表推，不写死。

实测（TC73，1080×2160）：模板1 → 横框；模板2 → 近正方；模板3 → 竖框 855×1196 点（长宽比 0.71，
与 70/100 = 0.70 一致）。

### 2. 模板3 尺寸：70×40 → **70×100**（纵向标签）

| 模板 | 纸面 | 点阵（203dpi） | 长宽比 |
|---|---|---|---|
| 模板1 | 60×40 mm | 480×320 | 1.50（横） |
| 模板2 | 70×70 mm | 559×559 | 1.00（方） |
| **模板3** | **70×100 mm** | **559×799** | **0.70（竖）** |

改动落在两处真源（Python `tools/zpl_geometry.TEMPLATES` 与 Kotlin `ZplGeometry.TEMPLATES`）：

- Kotlin 与 Python 模板表各一处；
- `tools/regress.py` 的常量自检与模板集合断言（`559×799`）；
- README 的模板表说明；
- 取景框长宽比随之变化（模板3 现在是竖框）。

**副作用（已确认）**：`templateForAspect` 的自动选模板结果会变。现在模板3 的长宽比是 0.7，
所以**竖幅照片**（长宽比 <1）会优先命中模板3；而 2.4:1 那种宽条带照片此前命中的也是模板3，
现在改命中模板1（|ln(2.4/1.5)| = 0.47 < |ln(2.4/0.7)| = 1.23）。

标题行右侧 `V1.1`，从 `PackageManager` 读（唯一真源仍是 `build.gradle.kts` 的 `versionName`）。

### 4. 修「取景所见 ≠ 拍到的照片」（用户报"取景的内容和拍摄后的图片差异较大"）

根因是两侧画幅不一致：

| | 修改前 | 修改后 |
|---|---|---|
| Preview | `Preview.Builder().build()`，**没指定分辨率** → 由 CameraX 自选（常是 16:9 或其它比例） | 显式 `AspectRatioStrategy.RATIO_4_3_FALLBACK_AUTO_STRATEGY` |
| ImageCapture | 4:3 + 最高分辨率 | 4:3 + 最高分辨率（不变） |
| PreviewView.scaleType | 默认 `FILL_CENTER` → **裁掉画面两侧**去填满又窄又高的容器 | `FIT_CENTER` → 不裁切 |
| 预览容器 | `weight(1f)` 任意比例 | `aspectRatio(3:4)`（竖持时的 4:3 画幅；横持 4:3） |

后果与量级：4:3 画面被 FILL_CENTER 塞进约 0.72 比例的容器时，**只看得到约 54% 的横向视野**
（若预览缓冲是 16:9 则只剩约 40%），而照片是完整 4:3 —— 用户看到的就是"框里和拍出来的不一样"。

实测（TC73）：`CAMERA >>> bound｜preview=1600x1200 capture=4080x3060 scaleType=FIT_CENTER`，
两侧都是 4:3。另加一条告警：预览分辨率若不是 4:3（aspect fallback）会在日志里
`CAMERA >>> 预览画幅 … 不是 4:3`。

帧级复核：把预览容器裁剪与照片缩放到同尺寸做归一化互相关，"预览=整幅照片"假设得分最高
（0.373），任何"只显示横向 90/80/70/60%"的假设都依次更低（0.354/0.324/0.286/0.259）
—— 单调下降即为**预览覆盖整幅画面**的证据。

### 5. 新增调试口：保存拍摄原图（`--es savephoto 1`）

落盘到 `files/last_shot.png`，日志 `PHOTO >>> saved …`。取回：

```bash
adb exec-out run-as com.tiaomabang.labelreprint cat files/last_shot.png > shot.png
```

用处：验证"取景框所见 == 拍到的照片"时，**桌面截图不能当证据**（截图本身会被预览缩放带偏），
必须拿原图做对照。注意必须用 `exec-out`：MSYS/Git-Bash 的 `>` 重定向会把二进制换成 CRLF、PNG 读不回来。

## 取景框现在是有语义的：框外结果不参与识别

之前取景框只是画在预览上的视觉辅助，照片整个画面都会被 OCR —— 用户报"取景框外、上面图像标签
还是被一起 OCR"。现在**没检出标签边框时**，取景框矩形会传进流水线，**框外的要素一律丢弃**：

```
FRAME >>> frame_test.png full 模板1 没检出标签边框：按取景框 1243x829 取内容（框外不参与识别）
PLAN  >>> frame_test.png 2400x964 basis=full elements=4
DROP  >>> 「打印机自带标签9876543210」在取景框外，丢弃
```

设计取舍（都踩过）：

- **不裁像素，只丢结果**。裁像素看着更"干净"，但标签长宽比和模板不一致时（2.4:1 的条带放进
  3:2 的框）会把标签两端切掉 —— 少识别几个字可以重拍，缺了条码右半截只能重来。
- 判据用要素**中心点**是否在框内，压着框边的算框内，免得贴边摆放的标签被擦边误杀。
- 几何只有一份实现：`label/CaptureFrame.kt`。UI（画框）和流水线（过滤）共用，两边各写一份迟早漂移，
  用户就会看到"框跟实际处理范围对不上"。
- **检出标签边框时取景框不参与过滤**：那时工作图已被校正成标签本身，框不再代表内容范围。
- 丢弃原因进 `dropped` 列表，结果页可见 —— 用户少看到几个要素时能自己判断是不是框摆小了。

验证用图 `assets/samples/frame_test.png`（`drug_like.png` + 贴顶一行"打印机自带标签 9876543210"），
跑 `--es asset frame_test.png --es ocr 1`：要素数与 `drug_like.png` 相同（4），那行在框外被丢弃。

## 拍照自动备份（外部目录，免权限）

每次**拍照**都把原图存一份到：

```
/sdcard/Android/data/com.tiaomabang.labelreprint/files/shots/20261015_223751.jpg
```

- 外部应用目录：**不需要任何权限**、卸载即清、手机文件管理器和 USB 都能直接翻。
- 用 **JPEG(q92)** 而不是 PNG：同样 12MP，PNG 约 9MB、JPEG 约 1.3MB（实测 3060×4080 → 1271KB）。
  验收看的是内容和几何，不是像素级无损。
- 文件名 `yyyyMMdd_HHmmss.jpg`（带**秒**，同一分钟内连拍不会互相覆盖）。
- 存的是**未缩放的原图**（12MP），但落盘前不动流水线的那份 8MP 缩放。
- 相册选图不备份：原文件本来就在磁盘上。
- **不自动清理**（用户没要求，删他的文件比占空间更糟）。日志每张一行：
  `PHOTO >>> backup <path> <WxH> <KB>`，`adb shell ls .../shots/` 可查。
- 私有目录里那份 `files/last_shot.png`（`--es savephoto 1`，PNG 全无损）保留，用于像素级对照。

实测：装包 → `adb shell input tap` 按快门 → 日志出 backup 行、目录里出现 1271KB 的 JPEG。
